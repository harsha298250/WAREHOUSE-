## 2. Environment Variables

All sensitive configuration **must** be passed via environment variables. Never hardcode secrets.

### Step 1: Copy the example file
```bash
cp .env.example .env
```

### Step 2: Fill in real values

| Variable | Required | Description |
|---|---|---|
| `ENVIRONMENT` | Yes | `development` or `production` |
| `DB_USER` | Yes | MySQL username |
| `DB_PASSWORD` | Yes | MySQL password |
| `DB_HOST` | Yes | MySQL hostname |
| `DB_PORT` | No | MySQL port (default: 3306) |
| `DB_NAME` | Yes | MySQL database name |
| `DB_SSL_CA` | No | Path to SSL CA cert for cloud MySQL |
| `JWT_SECRET_KEY` | Yes | Random secret for JWT signing |
| `INITIAL_ADMIN_PASSWORD` | Yes | Initial admin account password |
| `CORS_ORIGINS` | Yes | Allowed frontend origins (comma-separated) |
| `GOOGLE_CLIENT_ID` | No | Google OAuth client ID |
| `GOOGLE_CLIENT_SECRET` | No | Google OAuth client secret |
| `GOOGLE_REDIRECT_URI` | No | Google OAuth redirect URI |
| `SMTP_HOST` | No | Email host (e.g., smtp.gmail.com) |
| `SMTP_PORT` | No | Email port (587 for TLS) |
| `SMTP_USER` | No | Email username |
| `SMTP_PASSWORD` | No | Email app password |
| `ALERT_EMAIL_TO` | No | Alert recipient email |
| `AWS_ACCESS_KEY_ID` | No | S3/B2 access key |
| `AWS_SECRET_ACCESS_KEY` | No | S3/B2 secret key |
| `AWS_REGION` | No | S3/B2 region |
| `AWS_S3_BUCKET` | No | S3/B2 bucket name |
| `AWS_ENDPOINT_URL` | No | Custom endpoint for B2/MinIO |

### Generate a secure JWT secret:
```bash
python -c "import secrets; print(secrets.token_hex(32))"
```

## 3. MySQL Setup

### Local MySQL
```sql
CREATE DATABASE warehouse_db;
CREATE USER 'warehouse_app'@'localhost' IDENTIFIED BY 'YourSecurePassword';
GRANT ALL PRIVILEGES ON warehouse_db.* TO 'warehouse_app'@'localhost';
FLUSH PRIVILEGES;
```

### Cloud MySQL (e.g., PlanetScale, Railway, AWS RDS)
Set `DB_HOST`, `DB_USER`, `DB_PASSWORD`, `DB_NAME`, and optionally `DB_SSL_CA`.

## 5. Database Migrations

> **Current Status**: The project uses SQLAlchemy `create_all()` for table creation, which is safe and idempotent.
> Alembic is configured as a baseline for future schema changes.

### First-time table creation
```bash
python backend/init_db.py
```
This is safe to run multiple times — it only creates tables that don't exist.

### Using Alembic (for schema changes in production)
```bash
# Create a new migration
alembic revision --autogenerate -m "describe your change"

# Review the generated migration in alembic/versions/

# Apply the migration
alembic upgrade head

# Rollback one step
alembic downgrade -1
```

> ⚠️ **Always review autogenerated migrations before running in production.**
> Alembic may generate DROP TABLE or DROP COLUMN statements if models change.

## 6. Demo Data Setup

> **IMPORTANT**: Demo data seeding is **NOT automatic** in production.
> It must be run manually by a developer.

```bash
# Local (direct)
python backend/seed_demo_data.py

# Docker
docker exec warehouse_platform_web python backend/seed_demo_data.py

# Render (after deployment)
render run python backend/seed_demo_data.py
```

> ⚠️ `seed_demo_data.py` **DELETES all existing warehouse data** before reseeding.
> Never run this in production unless you intend to reset all data.

## 7. Google OAuth Setup

### Prerequisites
1. Go to [Google Cloud Console](https://console.cloud.google.com/)
2. Create a new project or select existing
3. Enable **Google Sign-In API**
4. Create **OAuth 2.0 Client ID** (Web application type)
5. Add **Authorized JavaScript origins**: `https://your-domain.com`
6. Add **Authorized redirect URIs**: `https://your-domain.com/auth/google/callback`

### Configure
```env
GOOGLE_CLIENT_ID=your-client-id.apps.googleusercontent.com
GOOGLE_CLIENT_SECRET=your-client-secret
GOOGLE_REDIRECT_URI=https://your-domain.com/auth/google/callback
```

### Behavior
- New Google users are assigned **VIEWER** role by default
- Admin can promote roles via the admin panel
- Invalid tokens, wrong audience, expired tokens are all rejected server-side

## 9. Render Deployment

### Steps
1. Push your code to a GitHub repository (ensure `.env` is in `.gitignore`)
2. Go to [Render Dashboard](https://dashboard.render.com/) → **New → Web Service**
3. Connect your GitHub repository
4. Render auto-detects `render.yaml` for configuration
5. Set the following **secret environment variables** in the Render dashboard:
   - `DB_HOST` — your MySQL hostname
   - `DB_USER`, `DB_PASSWORD` — MySQL credentials
   - `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `GOOGLE_REDIRECT_URI`
   - `SMTP_USER`, `SMTP_PASSWORD`, `ALERT_EMAIL_TO`
   - `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` (if using cloud storage)
   - `CORS_ORIGINS` — your Render app URL: `https://warehouse-cloud-platform.onrender.com`
6. Deploy

### After deployment
```bash
# Create initial database tables
render run python backend/init_db.py

# Seed demo data (optional, data-destructive)
render run python backend/seed_demo_data.py
```

### Health Check URL
```
https://warehouse-cloud-platform.onrender.com/health
```

> **Note**: Render free tier may sleep after inactivity. The first request after sleep takes ~30 seconds.
> The health check endpoint keeps the service awake when pinged regularly.

## 11. Production Configuration

### Required for production
```env
ENVIRONMENT=production
JWT_SECRET_KEY=<64-char random hex>
DB_PASSWORD=<strong password>
CORS_ORIGINS=https://your-domain.com
```

When `ENVIRONMENT=production`:
- Application **refuses to start** if `JWT_SECRET_KEY` is the default dev string
- All authentication errors are sanitized
- Debug mode is disabled

### Performance
- `uvicorn --workers 1` is used (appropriate for Render free tier)
- For higher traffic, increase workers or use gunicorn

## 12. Troubleshooting

| Problem | Solution |
|---|---|
| `JWT_SECRET_KEY not configured` | Set a real random value in `.env` or Render env vars |
| `Database connection failed` | Check `DB_HOST`, `DB_PASSWORD`, MySQL service running |
| `CORS error in browser` | Add your frontend URL to `CORS_ORIGINS` env var |
| `Google Sign-In rejected` | Check `GOOGLE_CLIENT_ID` and redirect URI match exactly |
| `Email alerts not sending` | Use Gmail App Password (not regular password), enable 2FA |
| `Seed data command deleted production data` | Restore from MySQL backup — never run seed on production |
| Container fails health check | Check logs with `docker logs warehouse_platform_web` |

- [ ] `JWT_SECRET_KEY` is a random 64-char hex string
- [ ] `.env` is in `.gitignore` and not committed

## 14. Rollback Considerations

### Database rollback
```bash
# Alembic rollback (if migrations used)
alembic downgrade -1   # Roll back one step
alembic downgrade base  # Roll back all migrations
```

### Application rollback
- Render: Use the **Deploy History** tab to redeploy a previous version
- Docker: Tag images with versions (`warehouse-platform:v3.0`) for easy rollback

### Data backup before destructive operations
```bash
# Before running seed_demo_data.py, always backup:
pg_dump -h localhost -U postgres -d warehouse_db > backup_$(date +%Y%m%d_%H%M%S).sql
```

## 15. Grafana Observability Dashboard (Local Demo)

> **Scope**: This is a local/demo-time setup only — it is **not** deployed to Render.com production.

The project includes a pre-built Grafana observability dashboard that auto-provisions on startup via Docker Compose. It visualizes API throughput, latency, robot fleet utilization, simulation tick performance, and more — all scraped from the application's Prometheus `/metrics` endpoint.

### Quick Start

```bash
docker-compose up -d
```

This starts all services including:
- **Prometheus** at `http://localhost:9090` — scrapes `web:8000/metrics` every 15s
- **Grafana** at `http://localhost:3000` — auto-provisions the dashboard

### Accessing the Dashboard

1. Open `http://localhost:3000` in your browser
2. Login with default credentials: **admin / admin** (skip the password change prompt)
3. Navigate to **Dashboards** → **Warehouse OS - Technical Observability Dashboard**

### Dashboard Panels

| Panel | Metric Source |
|---|---|
| API Request Throughput | `http_requests_total` |
| API Latency (p95) | `http_request_duration_seconds` |
| Active Database Connections | `database_connections_active` |
| Celery Task Failures | `celery_tasks_total{status="failed"}` |
| Robot Fleet Utilization | `robot_utilization_ratio` |
| Simulation Tick Duration | `simulation_tick_duration_seconds` |
| Active Tasks by Priority | `warehouse_active_tasks_total` |

### Files

- `grafana/observability_dashboard.json` — Dashboard definition
- `grafana/provisioning/datasources/prometheus.yml` — Datasource auto-provisioning
- `grafana/provisioning/dashboards/dashboard.yml` — Dashboard auto-import config
- `prometheus.yml` — Prometheus scrape configuration

## 16. Cloud Services Integration Guide

The system supports real integrations with external cloud services. Configuring them is completely optional; the system will fallback automatically to mock/offline behaviors if credentials are not configured in `.env`.

### A. Upstash Redis (Cache & Session Broker)
- **Service**: Upstash Serverless Redis
- **Config**: Set `REDIS_URL` to your Upstash connection string (e.g., `rediss://default:token@host:port`).
- **Use Case**: Used for caching item forecast results and storing Celery task states.

### B. CloudAMQP RabbitMQ (Event Messaging Broker)
- **Service**: CloudAMQP Serverless RabbitMQ
- **Config**: Set `RABBITMQ_URL` to your AMQP URL (e.g., `amqp://user:password@host/vhost`).
- **Use Case**: Broker for Celery tasks and event-driven logging.

### C. Celery Worker (Asynchronous Workflows)
- **Config**: Set `CELERY_ENABLED=true` to enable Celery-backed queuing for emails, reports, and backups.
- **Run Worker**: Run `celery -A backend.celery_app.celery worker --loglevel=info` (or run via Docker Compose).

### D. Sentry (Error Telemetry)
- **Service**: Sentry.io FastAPI Integration
- **Config**: Set `SENTRY_DSN` to your Sentry key.
- **Verification**: Admins can trigger a test exception by calling `POST /health/sentry-test`.

### E. Resend (Email Alert Dispatch)
- **Service**: Resend.com SDK
- **Config**: Set `RESEND_API_KEY` to your Resend api key.
- **Verification**: Alerts and security OTP passkeys will be dispatched to the email configured.

### F. Backblaze B2 (Logical DB Disaster Recovery Backups)
- **Service**: Backblaze B2 (via boto3 S3 API)
- **Config**: Set `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_S3_BUCKET`, `AWS_REGION`, and `AWS_ENDPOINT_URL` to your B2 bucket.
- **Verification**: Backup creation uploads to B2, verifies matching file size, downloads the backup file to recalculate the SHA-256 checksum, and restores it in an isolated in-memory SQLite database to run schema validations.

### G. Google Gemini API (WMS Operations AI Explainer Assistant)
- **Service**: Google Generative AI REST API
- **Config**: Set `GEMINI_API_KEY` and optional `GEMINI_MODEL` (defaults to `gemini-1.5-flash`).
- **Use Case**: Provides natural language operational context explanations and risk mitigation advice based on real DB metrics.

### H. Google OAuth (Sign-In Interface)
- **Service**: Google Identity Services Sign-In
- **Config**: Set `GOOGLE_CLIENT_ID` to enable Google Authentication.
